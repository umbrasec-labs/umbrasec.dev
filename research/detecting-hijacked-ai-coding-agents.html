What a Hijacked AI Coding Agent Leaves in Your Logs

An AI coding agent runs shell commands with a developer's access. When something other than the developer steers it, those commands still look like the agent's work. This article covers what a hijacked agent leaves in your logs and ships three detections for it, with their limits stated.

Updated 2026-10-28: Honest limitations now covers Defender's SensitiveFileRead event, Microsoft's description of it, and a query to see what it records before relying on it for file reads.

Updated 2026-10-27: Cursor, Devin and Copilot coverage. Detection 1 now also covers the Cursor CLI, the Devin CLI and more Copilot CLI forms. Detection 2 adds the Copilot CLI, Cursor's wrapper shells and the legacy Windsurf terminal. Detection 3 adds the shells of the Copilot harness, the new default for Copilot in VS Code. The new strings rest on shipped code, vendor docs or user reports, not on a capture.

AI Coding Agents Confused Deputy Sigma KQL

A coding agent is a confused deputy by design. It holds the developer's shell, files and cloud sessions, and it acts on text it reads. If that text comes from someone else, the agent does their work with the developer's access. Three real cases show the range. In the Nx "s1ngularity" compromise (August 2025), malicious package versions started whichever agent CLI was installed, headless and with its permission prompts switched off, and told it to inventory secrets and wallet files. Amazon Q Developer for VS Code 1.84.0 (CVE-2025-8217) shipped with an injected instruction to run the Q CLI with every tool trusted and no interaction; it did not run because of a syntax error. Roo Code (CVE-2026-110202 to 110206) is the third shape: planted text in content the agent reads, and an auto-approve allowlist that the shell reads differently. It has no fix because the project is archived; see When the Allowlist Isn't a Boundary.

This article ships three detections for that surface: a Sigma rule for an agent CLI started headless with approvals off, a Sigma rule for an agent's shell doing something risky, and a Defender XDR KQL hunt for the VS Code terminal (as shipped, Windows only) and for the shells of Copilot's VS Code harness. Before this article the sigma-pack had no detection for coding agents. Different agents launch commands in different ways, so each detection sees some agents and not others, and the article says which. Both rules are tagged ATT&CK T1059 (Command and Scripting Interpreter), and the shell rule adds T1698 (Indirect Prompt Injection), T1552.001 (Credentials In Files) and T1105 (Ingress Tool Transfer).

"Visible" here means the command text sits on a process command line and that process can be tied to the agent. Each row describes the agent's default mode in the version the research read, and settings change it: a sandbox can put bwrap or sandbox-exec between an agent and its shell, and Roo Code and Cline can each switch between their own shell and the editor terminal. The detection sections below say which branch sees which row.

Detection 1: an agent CLI started headless with approvals off

The s1ngularity packages started an agent CLI with a prompt on the command line, no interactive session and the permission prompts switched off, and the Amazon Q injection would have done the same had it run. That launch is a single process with every part of it in CommandLine, so one Sigma process_creation rule sees it on Windows, macOS and Linux. For six of its seven CLIs the rule needs three things at once: the agent's image, its bypass flag and its headless flag. A bypass flag alone is how people run an agent by hand in a throwaway container, and a headless run with prompts left on is ordinary scripting, so neither fires on its own. There is no parent condition: s1ngularity started the agent from node, Amazon Q's injected line would have gone through a shell, and CI uses both. In August 2025 Claude Code was an npm package run by node, so the rule also matches node with claude on its command line. An npm install of the Copilot CLI runs a node loader that starts the native copilot with the same flags, so one such run would give two matching rows (read in the loader's shipped code).

The seventh is the Cursor CLI. It runs as node on every OS, so the rule keys on node with cursor-agent and index.js on its command line, plus --force, -f or --yolo. It needs no headless flag, because the CLI is headless whenever stdin or stdout is not a terminal, so an interactive Run Everything session matches too, and so does a prompt that contains -f, such as rm -f. The Devin CLI matches as devin from a bin folder, never the Devin.exe editor, with --permission-mode dangerous, yolo or bypass and -p or --print. Copilot also matches a bare shell grant, --allow-tool=shell or --allow-tool shell on its own or first in a list, and its headless flags now include -p at the end of the line and --acp. The flags are in the vendors' docs and the Cursor and Devin image paths are read in shipped code; none of it is captured. Copilot in VS Code, the Cursor editor and Devin Desktop keep approvals-off in the app's own settings, so none of them is matched.

Several gaps are deliberate and stated in the rule. A Copilot run that passes only --allow-all-tools gets through, and so does COPILOT_ALLOW_ALL, which leaves nothing on the command line. Copilot's docs say a -p run with no permission options denies every approval-gated request, so a pipeline that needs the shell passes --allow-all-tools, an --allow-tool grant or --assisted-approval. --allow-all-tools is the common CI form, so matching it alone would fire on every pipeline; the rule matches --allow-all, --yolo and a bare shell grant instead. A grant with shell after another tool (write,shell) is not matched, and neither is one quoted after a space where the sensor records the quotes (Windows); a Linux or macOS argv sensor strips them, so that form matches. Cursor's approvalMode "unrestricted" in the user's cli-config.json and Devin's DEVIN_PERMISSION_MODE switch approvals off with nothing on the command line. A Gemini positional prompt without -p is left out because in a terminal it opens an interactive session. Under node, Gemini's -y is not matched either, because npx -y uses the same letter for itself. Codex is matched on its long bypass flag and on --yolo, which Codex's source defines as an alias of it; --not-so-yolo is an alias of --approve-for-me, which sends approval requests to automatic review, so it stays quiet. CI runners and agent sandboxes run agents exactly like this by design: scope the rule by host group rather than dropping a flag. The sigma-pack holds the canonical copy.

Detection 2: an agent's shell doing something risky

Most hijacks end the same way: the agent runs a command through the shell it already has. Many agents start a fresh shell for every command, with the whole command on that shell's command line, so one Sigma process_creation rule can see two things at once: that the shell belongs to an agent, and that the command is one a developer almost never asks an agent for. The rule recognises the agent in four ways: by its parent process, by a wrapper string the agent writes onto its own shell command line, by a wrapper string on the command line of the shell's parent, or by a VS Code extension host as the direct parent. Then it needs one of four risky shapes: a credential file or token source named on the command line, a download piped into an interpreter, a download run through command substitution, or a DNS lookup built from a command substitution.

Several of these markers need a label. The Claude Code wrapper string comes from watching Claude Code 2.1.310 on Linux, not from documentation, and can change in any release. The Copilot CLI's shell shape is seen in user reports for 1.0.60 to 1.0.80, and that the command text sits on that shell's command line is inferred; a session-reuse path with an unknown shape also exists. The Copilot wrapper variable and the Cursor and Windsurf strings are read in shipped code, not captured. The extension-host branch matches any extension that spawns a shell directly: that is how Roo Code's default mode is seen, but nothing in it is specific to Roo. The Cursor and Devin Desktop extension hosts are not listed, and VS Code Insiders builds and the Linux editor process are left out because their process names are not confirmed. A sandboxed Codex, Kilo Code or Copilot run can put a hop such as bwrap or sandbox-exec between the agent and its shell, so the parent branch can miss it; the Claude Code wrapper branch does not depend on the parent.

Cursor needs its own explanation. On macOS and Linux the Cursor CLI and IDE agent hand each command to a bash or zsh wrapper shell on a file descriptor, not on its command line, so the rule sees only what the command starts, as a child of that wrapper (inferred). The wrapper shell expands the command first, so a credential read or gh auth token matches, but a plain curl | sh splits into two sibling children and is not matched, and neither is a plain download run through $( or <(. A command that itself runs another shell's -c, such as bash -c 'curl ... | sh', keeps that text on its child and matches. On Windows Git Bash the command is on the wrapper's own line, and one command can give two or three matching rows (inferred). Cursor's default Windows executor runs PowerShell with the command only inside a temporary .ps1 file, so it is not covered, and neither are Devin Local and the Devin CLI, whose shell launch is inferred, not confirmed. The Windsurf wrapper exists only in Cascade's dedicated terminal on macOS and Linux, from Windsurf 1.13.3 until Cascade's removal in Devin Desktop 3.9.19, so only older builds fire it.

The risky shapes are cut to what ordinary agent work does not do. Reading a .env file and piping into python are not matched, and a substitution only counts when something runs the download (after -c, after eval, or as process substitution read by a shell or source), so a version lookup into a variable, a diff against an API response or a commit message that mentions curl stays quiet. The rule's false positives name what still fires, such as a vendor's curl | sh installer, a search that names a credential file, or ssh-keygen writing a new key. It also fires when the agent itself uses gh auth token for ordinary work, such as GH_TOKEN=$(gh auth token) gh ... for a multi-account user or a hook, status-line or MCP server command in the agent's own configuration, and, once per Cursor session, whatever the user's own shell start-up files run under the state-snapshot login shell (an ssh-add of a key in .bashrc, for example); those repeat, so allowlist the exact command rather than drop gh auth token, because a hijacked agent printing the token is the case to catch. Agents that type into the editor's integrated terminal, such as GitHub Copilot in VS Code under its Local harness, are invisible to this rule, and the default Copilot harness is not expected to be seen either: its shells run under copilot-runtime, which the rule does not list, and on Windows and macOS the runtime types commands into one persistent shell (read in VS Code source), so no wrapper string is expected on a command line. The sigma-pack holds the canonical copy.

Detection 3: hunting the editor terminal

Agents that type into the editor's integrated terminal (GitHub Copilot in VS Code under its Local harness, Cline's default mode and Roo Code's terminal mode) leave nothing a Sigma rule can key on: the terminal's shell is the same one a person opens, and only the programs it starts become processes. Microsoft Defender XDR records one level more than Sigma's process_creation: DeviceProcessEvents names each child's grandparent, though as a file name only. That is enough to ask a narrower question: which commands run in a VS Code terminal named a credential source, or fetched something and ran an interpreter straight after? This is a hunt, not an alert. It cannot tell an agent from the person at the keyboard.

The query keeps the children of a shell whose parent is Code.exe and whose command line loads VS Code's shell-integration script (shellIntegration.ps1 for PowerShell, --init-file with shellIntegration-bash.sh for bash). Then it needs one of two things. The credential branch matches the same credential strings as Detection 2. The pairing branch takes a child whose command line names a download tool and a different child, an interpreter (sh, bash, python, the Windows py launcher, node, pwsh or powershell), that starts in the same shell up to 60 seconds later. It does not check that the interpreter runs what was downloaded, so curl fetching a test fixture followed by python -m pytest pairs too. That is the query's main false positive, and the reason it is a hunt.

Copilot in VS Code moved in 1.143. The release notes make the Copilot harness the default for new sessions, and VS Code source shows it rolls out as an experiment, so an install with experiments off probably keeps the Local harness (inferred). Under the Copilot harness the shells are started by copilot-runtime, the Copilot SDK runtime that VS Code bundles, not by the integrated terminal; that parent relation is read in VS Code source and the shipped SDK, not captured. So the query has a second source: the children of a shell whose parent is copilot-runtime, with no shell-integration condition, because the runtime's shells do not load VS Code's scripts (inferred from the SDK's strings). A Source column names the source of each row, vscode-terminal or copilot-harness, and both branches read both sources. The runtime keeps one persistent PTY shell per session on Windows and macOS (read in VS Code source), so a download and a later interpreter in that shell pair. On Linux VS Code asks the runtime for one shell per command; if the runtime honours that (not confirmed), a download and a later separate command do not pair, though a download and an interpreter that one command starts, such as bash -c "curl ... | sh", are children of one shell and can still pair. This source is a hunt too. Any Copilot SDK host gives the same parent, chat.agentHost.copilot.runtimePath can rename the runtime, the UI may be able to write into the runtime's terminals (inferred), and copilot-runtime starts with VS Code even when chat is not used (seen in a user report), so its presence alone shows no agent at work. Once per session on macOS and Linux the runtime's login-shell probe runs the user's profile under it (inferred), so a profile that runs curl and then node within 60 seconds pairs.

The terminal source is narrower than it looks. As shipped it covers PowerShell terminals in VS Code on Windows, because Code.exe is the only editor process name a public capture confirms; add the Linux or macOS name once you have checked what your sensor records. A cmd.exe terminal gets no shell-integration injection, so it is not seen. Git Bash gets the bash marker, but its process tree is not confirmed: it may put another bash.exe between the terminal and each command, which would hide its commands from the query. zsh, the macOS default, loads shell integration through ZDOTDIR and has no marker on its command line, so a zsh terminal is not seen at all. PowerShell cmdlets such as Invoke-WebRequest and Get-Content run inside the shell and start no process, which is an inference in the research rather than a capture. PowerShell records a native program by its quoted full path, so the query also matches gh.exe" auth token. Git Bash quotes the path only when it holds a space, so the query also matches gh.exe auth token. Both forms are inferred rather than captured. In a pipe such as curl ... | sh both processes start together, so the pair is found only when the download is recorded first or at the same moment. The sigma-pack holds the canonical copy, with these notes in its header.

        where ProcessCommandLine contains Tool
        | summarize DownloadHits = make_list(Tool))
    | where array_length(DownloadHits) > 0
    | project DeviceId, InitiatingProcessId, InitiatingProcessCreationTime,
              DownloadTime = Timestamp, DownloadProcessId = ProcessId,
              DownloadCommandLine = ProcessCommandLine;
// The few download children on the left, the many interpreter children on the right
let Pairs = Downloads
    | join kind=inner (TerminalChildren | where FileName in~ (Interpreters))
        on DeviceId, InitiatingProcessId, InitiatingProcessCreationTime
    // A different child, starting 0 to PairWindow after the download
    | where not(ProcessId == DownloadProcessId and Timestamp == DownloadTime)
    | where Timestamp between (DownloadTime .. DownloadTime + PairWindow)
    | extend Branch = "pairing";
union CredentialReads, Pairs
| project Timestamp, Branch, Source, DeviceName, AccountName, InitiatingProcessParentFileName,
          InitiatingProcessCommandLine, FileName, ProcessCommandLine, CredentialHits,
          DownloadTime, DownloadCommandLine
| sort by Timestamp desc

What this does not cover

  • Cursor and Devin beyond shipped code: the Cursor CLI and IDE agent strings and the Devin binary paths are read in the vendors' packages, and none of their shells has been captured. How Devin Desktop's agent (devin acp) and the Devin CLI start their shells is inferred, so Detection 2 does not cover them, and the Cursor and Devin Desktop extension hosts are not in its extension-host branch (see the table above).
  • Hidden command text: Cursor hands its wrapper shell each command on a file descriptor on macOS and Linux, so only what the command starts is seen, and on Windows its default PowerShell executor runs the command from a temporary .ps1 file, so its command line names nothing. Cline's background mode gives PowerShell, its default on Windows, the command on stdin behind a constant stub.
  • Approvals switched off without a matching flag: Copilot runs with only --allow-all-tools (see Detection 1), and a bypass set with nothing on the command line: Copilot's COPILOT_ALLOW_ALL, Devin's DEVIN_PERMISSION_MODE, Cursor's approvalMode "unrestricted" in cli-config.json, the editors' Run Everything and auto-approve toggles, or a settings file, where Claude Code can also take its permission mode.
  • Flag spellings Detection 1 does not read: short flags combined into one argument, flags wrapped in quotes where the sensor records the quotes (Windows), a Copilot shell grant after another tool in a list, and a Gemini -p as the last word on the line; the rule matches each flag after a space.
  • Other editor terminals: anything beyond VS Code PowerShell terminals on Windows for Detection 3's terminal source, and the opt-in custom terminal tool of Copilot's agent host, which neither of its sources sees (see Detection 3).
  • File reads: there is no file-access rule (see Honest limitations).
  • Config writes and MCP abuse: auto-approve written into .vscode/settings.json (Copilot, CVE-2025-53773, the 2025 behaviour; in VS Code 1.143.1 a workspace settings file cannot set chat.tools.global.autoApprove, read in VS Code source, though the user settings file can), a new MCP server entry (Cursor, CVE-2025-54135) or an approved one swapped for another command (Cursor, CVE-2025-54136). These are candidates for later rules.
  • Agent-native telemetry: no detection here reads an agent's own logs, which are the better signal where you can turn them on: Claude Code's OpenTelemetry export (with OTEL_LOG_TOOL_DETAILS=1 for the Bash command text) and its PreToolUse hooks, and VS Code's terminal.log, where its own agent terminal tool writes every command it runs.

Honest limitations

Each agent fingerprint in these detections, whether a process name, a flag or a wrapper string, was read from one version of an agent or editor, and any release can change it. Cursor and Devin coverage rests on vendor docs and shipped code, not on a capture: their CLI flags are documented, their wrapper strings and binary paths were read in shipped code, and how Devin Local and the Devin CLI start their shells is inferred, not confirmed, so Detection 2 leaves the Devin binary and the Cursor extension host out as shell parents rather than guessing. The Claude Code wrapper string that Detection 2 matches comes from watching Claude Code 2.1.310 on Linux, not from documentation, so no vendor commitment keeps it stable.

Credential access is seen only when a credential file or token command is named on a command line. An agent that reads a file through its own built-in tool starts no process at all, and Sysmon has no event for a file read. Detection 3 cannot tell an agent from the developer typing in the same terminal, so each row it returns is a lead to check, not a finding.

Defender for Endpoint may cover part of that gap. Its DeviceEvents table has an action type, SensitiveFileRead, that Microsoft Learn never names. The Defender portal's built-in schema reference (checked 2026-10-28) describes it as "A file that matched DLP policy was accessed or processes that are reading sensitive files such as ssh keys, Outlook mail archives etc." Nothing public says which files count, which operating systems record it, or whether the second half needs Purview DLP. We have not seen it record an agent reading a credential: the one tenant we could check runs no coding agents and holds no developer credentials, and there the event was mostly security and telemetry software reading Office files, mail archives and PDFs, with AdditionalFields always empty. Before you build on it, run this in your own tenant to see what it records: 

DeviceEvents
| where Timestamp > ago(30d) and ActionType == "SensitiveFileRead"
| summarize Events = count(), Devices = dcount(DeviceId)
    by InitiatingProcessFileName, Ext = tolower(extract(@"\.([^.\\/]+)$", 1, FileName))
| sort by Events desc

The KQL hunt has been parse-checked with the Kusto language service but has never run against a Defender XDR tenant, and the Claims Ledger marks its claims as not executed. None of the three detections has been run against a sensor capture on any OS, and on Windows the process names, the Git Bash process tree and the quoted path PowerShell records for a native program come from source code, public issue reports and inference. Both Sigma rules pass their claims on synthetic events built from the cited sources, which proves the rule logic, not your sensor's field names or formats. They are experimental: tune them against your own logs and read each file's false-positive notes before alerting on them.
