What a Hijacked AI Coding Agent Leaves in Your Logs

An AI coding agent runs shell commands with a developer's access. When something other than the developer steers it, those commands still look like the agent's work. This article covers what a hijacked agent leaves in your logs and ships three detections for it, with their limits stated.

AI Coding Agents Confused Deputy Sigma KQL

A coding agent is a confused deputy by design. It holds the developer's shell, files and cloud sessions, and it acts on text it reads. If that text comes from someone else, the agent does their work with the developer's access. Three real cases show the range. In the Nx "s1ngularity" compromise (August 2025), malicious package versions started whichever agent CLI was installed, headless and with its permission prompts switched off, and told it to inventory secrets and wallet files. Amazon Q Developer for VS Code 1.84.0 (CVE-2025-8217) shipped with an injected instruction to run the Q CLI with every tool trusted and no interaction; it did not run because of a syntax error. Roo Code (CVE-2026-110202 to 110206) is the third shape: planted text in content the agent reads, and an auto-approve allowlist that the shell reads differently. It has no fix because the project is archived; see When the Allowlist Isn't a Boundary.

This article ships three detections for that surface: a Sigma rule for an agent CLI started headless with approvals off, a Sigma rule for an agent's shell doing something risky, and a Defender XDR KQL hunt for the VS Code terminal, which as shipped covers Windows only. Before this article the sigma-pack had no detection for coding agents. Different agents launch commands in different ways, so each detection sees some agents and not others, and the article says which. Both rules are tagged ATT&CK T1059 (Command and Scripting Interpreter), and the shell rule adds T1698 (Indirect Prompt Injection), T1552.001 (Credentials In Files) and T1105 (Ingress Tool Transfer).

Detection 1: an agent CLI started headless with approvals off

The s1ngularity packages started an agent CLI with a prompt on the command line, no interactive session and the permission prompts switched off, and the Amazon Q injection would have done the same had it run. That launch is a single process with every part of it in CommandLine, so one Sigma process_creation rule sees it on Windows, macOS and Linux. For each of five CLIs the rule needs three things at once: the agent's image, its bypass flag and its headless flag. A bypass flag alone is how people run an agent by hand in a throwaway container, and a headless run with prompts left on is ordinary scripting, so neither fires on its own. There is no parent condition: s1ngularity started the agent from node, Amazon Q's injected line would have gone through a shell, and CI uses both. In August 2025 Claude Code was an npm package run by node, so the rule also matches node with claude on its command line.

Three gaps are deliberate and stated in the rule. Copilot needs --allow-all-tools for any programmatic run, so the rule matches only --allow-all and --yolo, and a run with --allow-all-tools alone gets through. A Gemini positional prompt without -p is left out because in a terminal it opens an interactive session. Under node, Gemini's -y is not matched either, because npx -y uses the same letter for itself. Codex is matched on its long bypass flag and on --yolo, which Codex's source defines as an alias of it; --not-so-yolo is an alias of --approve-for-me, which sends approval requests to automatic review, so it stays quiet. CI runners and agent sandboxes run agents exactly like this by design: scope the rule by host group rather than dropping a flag. The sigma-pack holds the canonical copy.

Detection 2: an agent's shell doing something risky

Most hijacks end the same way: the agent runs a command through the shell it already has. Many agents start a fresh shell for every command, with the whole command on that shell's command line, so one Sigma process_creation rule can see two things at once: that the shell belongs to an agent, and that the command is one a developer almost never asks an agent for. The rule recognises the agent by its parent process, by a wrapper string the agent writes onto its own shell command line, or by a VS Code extension host as the direct parent. Then it needs one of four risky shapes: a credential file or token source named on the command line, a download piped into an interpreter, a download run through command substitution, or a DNS lookup built from a command substitution.

Two of these markers need a label. The Claude Code wrapper string comes from watching Claude Code 2.1.310 on Linux, not from documentation, and can change in any release. The extension-host branch matches any extension that spawns a shell directly: that is how Roo Code's default mode is seen, but nothing in it is specific to Roo. Cursor, VS Code Insiders builds and the Linux editor process are left out because their process names are not confirmed. A sandboxed Codex or Kilo Code run can put a hop such as bwrap or sandbox-exec between the agent and its shell, so the parent branch can miss it; the Claude Code wrapper branch does not depend on the parent.

The risky shapes are cut to what ordinary agent work does not do. Reading a .env file and piping into python are not matched, and a substitution only counts when something runs the download (after -c, after eval, or as process substitution read by a shell or source), so a version lookup into a variable, a diff against an API response or a commit message that mentions curl stays quiet. The rule's false positives name what still fires, such as a vendor's curl | sh installer, a search that names a credential file, or ssh-keygen writing a new key. It also fires when the agent itself uses gh auth token for ordinary work, such as GH_TOKEN=$(gh auth token) gh ... for a multi-account user or a hook, status-line or MCP server command in the agent's own configuration; those repeat on every run, so allowlist the exact command rather than drop gh auth token, because a hijacked agent printing the token is the case to catch. Agents that type into the editor's integrated terminal are invisible to this rule. The sigma-pack holds the canonical copy. 

title: AI Coding Agent Shell Runs a Risky Command
id: 018f37c7-4f08-4bd4-8b4f-495a60116ff6
status: experimental
description: >
    A shell or tool started by an AI coding agent ran something a developer
    almost never asks an agent to run: it named a credential file or token
    source, piped a download into an interpreter, ran a download through
    command substitution, or built a DNS lookup from a command substitution.
    That is what an agent does with the shell it already has once indirect
    prompt injection or malware steers it. The agent is recognised in three
    ways. By its parent process: Claude Code's native binary (\claude.exe on
    Windows, the .local/share/claude/versions/ folder on macOS and Linux),
    codex, Kilo Code's bundled kilo server, and qchat from the Amazon Q
    Developer CLI. A sandboxed Codex or Kilo Code run can put a hop such as
    bwrap, sandbox-exec or codex-linux-sandbox between the agent and the shell,
    so the parent branch can miss it; the Claude Code wrapper branch does not
    depend on the parent. By a wrapper the agent writes onto its own shell
    command line: Gemini CLI's shopt -u promptvars nullglob extglob nocaseglob
    dotglob prefix, Kilo Code's PowerShell UTF-8 prologue, and Claude Code's
    shell-snapshots/snapshot- file, matched with / or \ separators. The Claude
    Code wrapper is a local observation of Claude Code 2.1.310 on Linux, not a
    documented interface, and can change in any release. By a VS Code
    extension host as the direct parent: Code.exe on Windows or Code Helper
    (Plugin) on macOS, with --inspect-port=0 on the parent command line. That
    branch matches any VS Code extension that spawns a shell directly, not one
    agent; it is how Roo Code's default mode, which runs each command through a
    shell from the extension host, is seen. Cursor, VS Code Insiders builds and
    the Linux editor process are left out, because their process names are not
    confirmed. Credential sources matched: .aws/credentials, SSH private keys
    under .ssh/id_, .kube/config, .codex/auth.json and a browser's Login Data
    file, each with / or \ separators; .npmrc, .git-credentials and gh auth
    token; CODEX_HOME/auth.json with / only; and /proc/PID/environ. Download
    and execute: curl, wget, Invoke-WebRequest, iwr, Invoke-RestMethod, irm or
    DownloadString on the same command line as a pipe into sh, bash, zsh, sudo
    sh, sudo bash, pwsh, powershell or iex, or as iex( or Invoke-Expression.
    Command substitution that runs a download: -c "$(curl, -c "`curl, eval
    $(curl, eval "$(curl, or process substitution read by bash, sh, zsh or
    source as a whole word (bash <(curl), each also with wget; and nslookup
    followed directly by $(. Not matched: a read of a .env file, which agents
    do all the time in project work; a pipe into python, because agents pipe
    API output into python -m json.tool; a download saved to a file and run by
    a later command; a download captured into a variable, or a command
    substitution inside a curl argument; process substitution read by any
    other command or by the . builtin; a pipe into a shell followed directly
    by a line break, or closed by ) inside a subshell; a pipe into sudo with
    options, or into node, perl or ruby; a shell reading process substitution
    straight after (, ; or && with no space; and agents that type into the
    editor's integrated terminal (GitHub Copilot agent mode, Cline's default,
    Roo Code's terminal mode), whose shells look the same as a user's.

Detection 3: hunting the editor terminal

Agents that type into the editor's integrated terminal (GitHub Copilot agent mode, Cline's default mode and Roo Code's terminal mode) leave nothing a Sigma rule can key on: the terminal's shell is the same one a person opens, and only the programs it starts become processes. Microsoft Defender XDR records one level more than Sigma's process_creation: DeviceProcessEvents names each child's grandparent, though as a file name only. That is enough to ask a narrower question: which commands run in a VS Code terminal named a credential source, or fetched something and ran an interpreter straight after? This is a hunt, not an alert. It cannot tell an agent from the person at the keyboard.

The query keeps the children of a shell whose parent is Code.exe and whose command line loads VS Code's shell-integration script (shellIntegration.ps1 for PowerShell, --init-file with shellIntegration-bash.sh for bash). Then it needs one of two things. The credential branch matches the same credential strings as Detection 2. The pairing branch takes a child whose command line names a download tool and a different child, an interpreter (sh, bash, python, the Windows py launcher, node, pwsh or powershell), that starts in the same shell up to 60 seconds later. It does not check that the interpreter runs what was downloaded, so curl fetching a test fixture followed by python -m pytest pairs too. That is the query's main false positive, and the reason it is a hunt.

The coverage is narrower than it looks. As shipped it covers PowerShell terminals in VS Code on Windows, because Code.exe is the only editor process name a public capture confirms; add the Linux or macOS name once you have checked what your sensor records. A cmd.exe terminal gets no shell-integration injection, so it is not seen. Git Bash gets the bash marker, but its process tree is not confirmed: it may put another bash.exe between the terminal and each command, which would hide its commands from the query. zsh, the macOS default, loads shell integration through ZDOTDIR and has no marker on its command line, so a zsh terminal is not seen at all. PowerShell cmdlets such as Invoke-WebRequest and Get-Content run inside the shell and start no process, which is an inference in the research rather than a capture. PowerShell records a native program by its quoted full path, so the query also matches gh.exe" auth token. Git Bash quotes the path only when it holds a space, so the query also matches gh.exe auth token. Both forms are inferred rather than captured. In a pipe such as curl ... | sh both processes start together, so the pair is found only when the download is recorded first or at the same moment. The sigma-pack holds the canonical copy, with these notes in its header. 

// A command in a VS Code terminal named a credential source, or one terminal shell ran a download and then an interpreter
let Lookback = 1d;
let PairWindow = 60s;
// Bare names: InitiatingProcessParentFileName holds no path
let Editors = dynamic(["Code.exe"]);
let ShellIntegrationMarkers = dynamic(["shellIntegration.ps1", "shellIntegration-bash.sh"]);
// The credential and download strings of ai-agent-shell-risky-command, plus
// gh.exe" auth token and gh.exe auth token: the forms inferred for gh started from
// PowerShell and from Git Bash on a path with no space (neither captured)
let CredentialMarkers = dynamic([".aws/credentials", @".aws\credentials", ".ssh/id_",
    @".ssh\id_", ".npmrc", ".git-credentials", "gh auth token", ".kube/config",
    @".kube\config", "/Login Data", @"\Login Data", @"/Login\ Data", ".codex/auth.json",
    @".codex\auth.json", "CODEX_HOME/auth.json", 'gh.exe" auth token',
    "gh.exe auth token"]);
// /environ, then a space, ', ", ;, ) or the end of the line
let ProcEnvironEnd = @"(?i)/environ([ '"";)]|$)";
let DownloadTools = dynamic(["curl", "wget", "Invoke-WebRequest", "iwr",
    "Invoke-RestMethod", " irm ", "(irm ", '"irm ', "'irm ", "DownloadString"]);
// py and py.exe are the Windows Python launcher
let Interpreters = dynamic(["sh", "sh.exe", "bash", "bash.exe", "python", "python.exe",
    "python3", "python3.exe", "py", "py.exe", "node", "node.exe", "pwsh", "pwsh.exe",
    "powershell", "powershell.exe"]);
let TerminalChildren = DeviceProcessEvents
    | where Timestamp > ago(Lookback)
    | where InitiatingProcessParentFileName in~ (Editors)
    | where InitiatingProcessCommandLine has_any (ShellIntegrationMarkers);
let CredentialReads = TerminalChildren
    | mv-apply Marker = CredentialMarkers to typeof(string) on (
        where ProcessCommandLine contains Marker
        | summarize CredentialHits = make_list(Marker))
    | where array_length(CredentialHits) > 0
        or (ProcessCommandLine contains "/proc/"
            and ProcessCommandLine matches regex ProcEnvironEnd)
    | extend Branch = "credential";
let Downloads = TerminalChildren
    | mv-apply Tool = DownloadTools to typeof(string) on (
        where ProcessCommandLine contains Tool
        | summarize DownloadHits = make_list(Tool))
    | where array_length(DownloadHits) > 0
    | project DeviceId, InitiatingProcessId, InitiatingProcessCreationTime,
              DownloadTime = Timestamp, DownloadProcessId = ProcessId,
              DownloadCommandLine = ProcessCommandLine;
// The few download children on the left, the many interpreter children on the right
let Pairs = Downloads
    | join kind=inner (TerminalChildren | where FileName in~ (Interpreters))
        on DeviceId, InitiatingProcessId, InitiatingProcessCreationTime
    // A different child, starting 0 to PairWindow after the download
    | where not(ProcessId == DownloadProcessId and Timestamp == DownloadTime)
    | where Timestamp between (DownloadTime .. DownloadTime + PairWindow)
    | extend Branch = "pairing";
union CredentialReads, Pairs
| project Timestamp, Branch, DeviceName, AccountName, InitiatingProcessParentFileName,
          InitiatingProcessCommandLine, FileName, ProcessCommandLine, CredentialHits,
          DownloadTime, DownloadCommandLine
| sort by Timestamp desc

What this does not cover

  • Agents with an unconfirmed launch chain: the Cursor IDE agent, Windsurf (now Devin Desktop), the Copilot CLI's own shell tool and the Copilot harness in VS Code (see the table above).
  • Hidden command text: the Cursor CLI hands its shell each command on a separate file descriptor by default (a -File script on Windows), and Cline's background mode gives PowerShell, its default on Windows, the command on stdin behind a constant stub.
  • Approvals switched off without a matching flag: Copilot runs with only --allow-all-tools (see Detection 1), and a bypass set through the COPILOT_ALLOW_ALL environment variable or in a settings file, where Claude Code can also take its permission mode.
  • Flag spellings Detection 1 does not read: short flags combined into one argument, flags wrapped in quotes, and a Gemini or Copilot -p as the last word on the line; the rule matches each flag after a space.
  • Other editor terminals: anything beyond VS Code PowerShell terminals on Windows (see Detection 3).
  • File reads: there is no file-access rule (see Honest limitations).
  • Config writes and MCP abuse: auto-approve written into .vscode/settings.json (Copilot, CVE-2025-53773), a new MCP server entry (Cursor, CVE-2025-54135) or an approved one swapped for another command (Cursor, CVE-2025-54136). These are candidates for later rules.
  • Agent-native telemetry: no detection here reads an agent's own logs, which are the better signal where you can turn them on: Claude Code's OpenTelemetry export (with OTEL_LOG_TOOL_DETAILS=1 for the Bash command text) and its PreToolUse hooks, and VS Code's terminal.log, where its own agent terminal tool writes every command it runs.

Honest limitations

Each agent fingerprint in these detections, whether a process name, a flag or a wrapper string, was read from one version of an agent or editor, and any release can change it. Agents whose process names or launch chain no public source confirms, such as Cursor and Windsurf (now Devin Desktop), are left out rather than guessed at. The Claude Code wrapper string that Detection 2 matches comes from watching Claude Code 2.1.310 on Linux, not from documentation, so no vendor commitment keeps it stable.

Credential access is seen only when a credential file or token command is named on a command line. An agent that reads a file through its own built-in tool starts no process at all, and Sysmon has no event for a file read. Detection 3 cannot tell an agent from the developer typing in the same terminal, so each row it returns is a lead to check, not a finding.

The KQL hunt has been parse-checked with the Kusto language service but has never run against a Defender XDR tenant, and the Claims Ledger marks its claims as not executed. None of the three detections has been run against a sensor capture on any OS, and on Windows the process names, the Git Bash process tree and the quoted path PowerShell records for a native program come from source code, public issue reports and inference. Both Sigma rules pass their claims on synthetic events built from the cited sources, which proves the rule logic, not your sensor's field names or formats. They are experimental: tune them against your own logs and read each file's false-positive notes before alerting on them.
