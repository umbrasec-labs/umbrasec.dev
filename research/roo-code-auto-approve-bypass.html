When the Allowlist Isn't a Boundary - Auto-Approve Bypasses in an Abandoned AI Coding Agent

An AI coding agent that can run shell commands keeps a list of commands it is allowed to run without asking. Five disclosed flaws in Roo Code show that the list was never a wall. The code that checks the command and the shell that runs it read it differently, so a command can pass the check and then do something else entirely. The instruction to run it does not even have to come from you. And there is no patch coming, because the project was archived in May.

AI Coding Agents Indirect Prompt Injection Excessive Agency Supply Chain

TL;DR for defenders. On 13 October 2026 VulnCheck disclosed five command auto-approve bypasses in Roo Code, an open-source AI coding agent for VS Code: CVE-2026-110202 through CVE-2026-110206, all affecting versions through 3.54.0. Each is a way to write a shell command that passes Roo Code's auto-approve allowlist but makes the shell execute something the allowlist would have denied. The trigger is indirect prompt injection: text planted in a file, repo, or page the agent reads, so no local access is needed. All five require auto-approval to be enabled. There is no fixed release: the Roo Code repository was archived on 15 May 2026 and is read-only. Do three things: find who still has Roo Code installed and move them off it; turn off auto-approval for command execution everywhere it survives; and treat any AI agent's command allowlist as a convenience, never a security boundary, running agents in a disposable environment that holds no production credentials.

The rail that makes auto-approve feel safe

An AI coding agent earns its keep by doing things, not just suggesting them: running the test suite, installing a dependency, grepping the tree. Asking a human to approve every single command destroys the point, so these tools offer auto-approval, usually gated by an allowlist. You permit a set of safe commands, say npm test or echo, and the agent runs anything matching the list without stopping to ask. The allowlist is the safety rail. It is the thing that makes handing a model a shell feel acceptable.

The five Roo Code CVEs are all the same shape: the rail has a gap, and the gap is structural rather than a typo. To decide whether a command is allowed, Roo Code parses it and checks the result against the list. To run it, the operating system shell parses it again. Those two parsers do not agree on every input. Anywhere they disagree, you can write something that the checker reads as a harmless allowlisted command and the shell reads as something else. This is a parser-differential bug, the same class that defeats many denylists and web filters, and it is very hard to get right because you are trying to predict a shell's full grammar in your own checker.

The five bypasses, at a defender's depth

We are describing what each flaw abuses, not how to weaponise it. No working command appears here. The point is the pattern: five different ways the checker and the shell disagree.

CVEWhat the checker and shell disagree about
CVE-2026-110202A redirect prefix makes getCommandDecision() judge the command by the redirect target rather than the command that actually runs.
CVE-2026-110203Escaped or single-quoted double quotes confuse the quote-masking regex in parseCommandLine(), hiding a command separator from the checker.
CVE-2026-110204A brace-style command substitution is read by the checker as a harmless parameter expansion, but executed as a substitution on bash 5.3+ or ksh93.
CVE-2026-110205A command substitution placed next to a glob character (* or ?) is dropped by the parser but still executed by the shell. CWE-184, CVSS v4.0 7.7.
CVE-2026-110206A command substitution in command position passes the echo allowlist check, and the shell runs its output as a command.

Five is the number that matters more than any single entry. One bypass is a bug; five, found in one pass over the same function, says the approach itself cannot be trusted to hold. A checker that has to re-implement a shell's grammar will keep losing to the shell, because the shell is the ground truth and the checker is a guess about it.

The instruction doesn't have to come from you

The second half of the problem is delivery. You might assume that to abuse the allowlist, an attacker has to type into your agent. They do not. The disclosed vector is indirect prompt injection: the attacker plants the instruction in content the agent reads on your behalf, a source file, a dependency's README, an issue, a web page the agent fetches, and the agent, doing its job, turns that text into a command. The allowlist is what was supposed to make that safe, because even a hijacked agent could only run allowlisted commands. These flaws remove that floor.

Put the two halves together and you have the agent threat surface we have written about before in Securing AI Agents: excessive agency (the agent can run commands at all), indirect injection (its instructions come from untrusted content), and the confused deputy (the agent acts with your privileges on an attacker's behalf). Roo Code is a concrete, dated instance of all three at once, with the one control meant to contain them removed.

No fix is coming

The detail that changes the response is maintenance status. The Roo Code repository was archived by its owner on 15 May 2026, and now carries a read-only banner stating the extension was shut down that day. Version 3.54.0 was its last release and remains the latest on GitHub. VulnCheck's advisories list no fixed version, because there is no one left to ship one.

This is the quiet half of the supply-chain risk in developer tooling. A library with a known CVE at least gets a red mark in your scanner. An editor extension that has simply stopped updating does not announce it. It keeps working, keeps its permissions, keeps running with the developer's full access to code, credentials and cloud sessions, long after the people who could fix it have moved on. "Install once, forget" is the default relationship most developers have with their extensions, and it is exactly the relationship an attacker counts on.

Why this is hard to see, and what to watch instead

You cannot write a neat request-signature rule for this the way you might for a web exploit. The malicious instruction is natural-language text buried in content the agent legitimately reads, and the command it produces is run by a normal developer tool on a developer's own machine. The signal is not in the request; it is in the behaviour of the endpoint.

  • The editor spawning surprising children. On an endpoint running VS Code with an agent, watch for the editor or its extension host process spawning shells, curl or wget, package managers invoked outside an install, or interpreters launched with inline code, especially command substitutions ($(...), backticks) in the command line. EDR process-ancestry telemetry is where this lives.
  • Egress from developer machines. A dev workstation suddenly resolving and connecting to an unfamiliar host, or writing to a staging directory then reaching out, is the same post-exploitation tell as any other code execution. Baseline where your developers' machines normally talk.
  • Inventory. Query your endpoint management or EDR for the Roo Code extension across the fleet. An archived extension will not prompt anyone to remove it, so its install base only shrinks if you go looking.
  • The generalised rule. Any agent with command auto-approval is a candidate for the same parser-differential gap. Treat the presence of auto-approve on an internet-reading agent as a finding in its own right, not just Roo Code. What a Hijacked AI Coding Agent Leaves in Your Logs covers this across agents and ships detections for it.

What to do

  1. Find it. Inventory the fleet for Roo Code (and any VS Code agent extension). You cannot act on what you have not counted.
  2. Move off it. It is archived and will not be fixed. Migrate anyone still using it to a maintained agent, and track that as the real remediation.
  3. Turn off command auto-approval wherever Roo Code remains in the meantime. Every one of these bypasses needs auto-approval on; without it, the human is back in the loop.
  4. Shrink and distrust the allowlist. For any agent, keep the auto-approve list minimal and treat it as a convenience, never a security control. The checker cannot out-parse the shell.
  5. Contain the blast radius. Run coding agents in a container or dev VM that holds no production credentials and has constrained egress, so a hijacked agent reaches nothing that matters. Limit the untrusted content agents ingest where you can.
  6. Make maintenance a gate. Add "is it still maintained, and when was its last release?" to the questions asked before any AI extension is approved, and re-check periodically.

Honest limitations

This article contains no working bypass command and does not reconstruct one; the table describes the class of parser disagreement each CVE abuses, from the public advisories. CVSS figures vary by source and version of the metric (several entries list 8.8 under CVSS v3.1; CVE-2026-110205 is 7.7 under v4.0); read the record for your own prioritisation. The indirect-injection vector and the requirement for auto-approval are as stated by VulnCheck. We have not tested the flaws. The detection guidance is behavioural and will vary with your EDR's visibility into editor process trees; validate it against your own telemetry before relying on it.
