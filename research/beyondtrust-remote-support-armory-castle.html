The Remote Support Appliance Was Open for Seven Weeks - CVE-2026-102764 and What ARMORY CASTLE Left Behind

A remote support appliance exists to reach every machine you support, holding the credentials to do it. That is exactly what makes it worth seven quiet weeks of an espionage group's time. CVE-2026-102764 is a critical authentication bypass in BeyondTrust Remote Support, exploited as a zero-day since late August 2026 before anyone knew it existed. The vulnerability is one sentence. What the operators built on the box afterwards is the part a defender has to read.

Privileged Access Third-Party Risk Threat Hunting Espionage

TL;DR for defenders. CVE-2026-102764 is an authentication bypass by spoofing (CWE-290) in BeyondTrust Remote Support, CVSS v4.0 9.3, letting an unauthenticated remote attacker perform file operations on the appliance. It was exploited as a zero-day from late August 2026 by ARMORY CASTLE (formerly UNC5221), a suspected PRC-nexus espionage actor. Affects all supported versions up to 26.2.3; patch BT26-05-RS covers 24.3.1 to 26.2.3, older builds must upgrade first, SaaS tenants were patched 9 October, and Privileged Remote Access shares the code and should be patched too. CISA added it to KEV on 16 October. The hard part: patching does not remove persistence. If an appliance was reachable on a vulnerable version during the window, treat it as potentially compromised, preserve evidence before you change anything, hunt the specific artifacts below, rotate credentials only after patching or rebuilding, and forward logs off the box.

The appliance is the point

BeyondTrust Remote Support (the product formerly called Bomgar) is the console a help desk uses to take control of the machines it supports. To do that job it sits in a privileged position: reachable, trusted, and holding or brokering the credentials needed to reach endpoints across the estate. Every property that makes it useful to your support team makes it valuable to an intruder. Compromise it and you are not at the edge of the network, you are at the hub of the one system built to touch everything else.

This is the same lesson as our writeup on the N-central RMM compromise, and it is not the first time this specific product has been the way in: the US Treasury breach of December 2024 ran through a stolen key for BeyondTrust's Remote Support cloud service. A tool that reaches everything is a tool worth breaking into, and it will be broken into again.

BeyondTrust is deliberately withholding lower-level exploitation detail, and so are we. The file-write primitive is the foothold; everything that matters to a defender is what the operators did with it, which is unusually well documented because Mandiant published it.

What ARMORY CASTLE left behind

Mandiant attributes the activity to ARMORY CASTLE, a suspected PRC-nexus espionage actor formerly tracked as UNC5221 and tracked by CrowdStrike as Warp Panda. The post-exploitation tradecraft is the detection surface, so it is worth walking through what the report describes.

SAWFLY: the web shell that answers 404

The first sign was a POST request to a crafted .php path. About eleven minutes later a PHP web shell, SAWFLY, was written into the appliance's Laravel public directory as mangoapi.php. Its design is built to stay invisible to scanning: if the request does not carry a specific parameter, the script immediately returns http_response_code(404) and exits, so a crawler or vulnerability scanner sees nothing but a missing page. Its traffic is wrapped in a custom Base32 transport with RC4, so the body is opaque.

The defensive implication is specific: you cannot find this by scanning for a live page, because it denies it exists. The visible signal is POST traffic to an unexpected .php path that returns 404, which is why logging request bodies and response sizes on the appliance's web tier matters more than status codes alone.

Root, and a foothold that survives a rebuild of config

From the web shell the operators escalated and dug in. The report describes privilege escalation by copying /bin/sh to a service-looking path, /usr/bin/dbus-authd, setting it root-owned and SUID. They attempted to dump the credential vault with /ns/sbin/bt-secrets, iterating through several CLI syntaxes, then deleted its log at /home/bomgar/log/bt-secrets.log. Most durably, they planted a persistence script at /home/bomgar/sbin/post_boot.d/zz-root-persist that appends a NOPASSWD sudo entry to /ns/config/sudoers.template and runs bt-sysconfig to rebuild /etc/sudoers. As Mandiant puts it, this "ensures the threat actor's privilege escalation survives system reboots and configuration resets."

That last detail is why a patch is not the end. The persistence is seeded into the appliance's own configuration-rebuild machinery, so it is designed to come back after exactly the kind of reset an operator might perform while remediating.

BARECLAW: a tunnel hidden behind the appliance's own proxy

For command and control the operators deployed BARECLAW, a SOCKS5 proxy written in C carried over WebSocket, as ingredi_ws in /tmp, bound to a local port. Rather than open a port to the internet, they edited the appliance's own /ns/config/haproxy.conf to add an ACL matching a chosen WebSocket path and a backend pointing at the local listener. The tunnel's listener is bound to localhost only, so it is invisible to an external port scan and can be reached solely through HAProxy's redirection, blending into normal HTTPS. A quiet flag suppresses the tunneler's own logging.

So the detection cannot rely on host logs or a visible open port. It relies on integrity of the HAProxy configuration (an unexpected ACL and backend), an unusual WebSocket path in proxy or network telemetry, and flow data.

Erasing the trail, and the tell it leaves

The actor routinely deleted appliance logs, including /ns/log/auth.log, /ns/log/ssl.log, /ns/log/http-access.log, /ns/log/php-fpm.log, /var/log/messages and /tmp/sshauth.*. Deletion is itself detectable if you are looking for the shape of it: Mandiant notes that "an interruption bounded by a single session is a strong indicator of log tampering." A clean gap that starts and ends with one session is not a logging glitch. The durable answer is to forward logs off the appliance, because an on-box log an attacker can reach is an on-box log an attacker can erase.

Lateral movement used a compromised Administrator account to log into /login and raise Jump Item and Team permissions from No Access to Administrator, recorded in syslog as a user_changed event.

The hunt

Mandiant published file hashes and YARA rules, which makes this one of the more actionable intrusions of the month. Use the published indicators, then hunt the behaviour, because indicators age and behaviour does not.

A caveat BeyondTrust states and we repeat: the absence of these indicators does not prove an appliance is clean. Self-hosted customers cannot fully audit the appliance host filesystem themselves and should coordinate host-level inspection with BeyondTrust Support.

What to do this week

  1. Patch. Apply BT26-05-RS to self-hosted Remote Support (24.3.1 to 26.2.3; older must upgrade first). SaaS tenants were patched 9 October. Patch self-hosted Privileged Remote Access too, since it shares the code; confirm the correct patch with BeyondTrust Support.
  2. Assume compromise for anything that was exposed. If an appliance was internet-reachable on a vulnerable version during the window (from late August), treat it as potentially compromised until reviewed. Patching does not remove persistence.
  3. Preserve evidence before you change anything. Snapshot memory and export the disk before rebooting or reconfiguring, because reboots and config resets are exactly what the persistence is built to survive.
  4. Hunt the artifacts above, then rotate credentials the appliance held or brokered - but only after patching or rebuilding, so you are not handing fresh secrets to an attacker who still has access.
  5. Forward logs off-box now with retention covering the full window. It cannot recover already-deleted evidence, but it ends the attacker's ability to erase what happens next.
  6. If your MSP runs it for you, ask them which build they are on, when they patched, whether they treated exposed appliances as compromised, and what they hunted for. The appliance is theirs; the access it brokers is to your fleet.

Honest limitations

This article contains no exploit code and no proof of concept; BeyondTrust is withholding low-level detail and so are we. The vulnerability classification and scoring are as reported by Rapid7 citing the CVE record and by BeyondTrust's advisory; one secondary source lists a different CVSS figure, so confirm against the record for your prioritisation. The intrusion tradecraft, file paths, hashes and YARA rule names are from the Google Threat Intelligence Group and Mandiant analysis; we have not independently reproduced them, and indicators like filenames and paths are operator choices that will differ in other intrusions. Hunt the behaviour, not only the strings. A public proof-of-concept repository exists for this CVE; we did not use it and do not link it.
